# EF Core Migration Lifecycle

This sandbox intentionally treats schema changes as reviewed source code, not as startup side effects.

## 1. Change the model

Modify domain/entity configuration first. The model is the intent; the migration is the database transition generated from that intent.

## 2. Create a migration

From `Study Sandbox/`:

```bash
dotnet tool restore

dotnet ef migrations add <MigrationName> \
  --project backend/Watchlist.Api \
  --startup-project backend/Watchlist.Api
```

For the baseline, the first migration is `20260917130000_InitialWatchlist`.

## 3. Review the diff

Always inspect:

- the migration `Up` operation;
- the `Down` operation;
- the model snapshot;
- table/column types;
- nullability;
- keys, indexes and constraints;
- destructive operations or implicit data loss.

A generated migration is a proposal, not an approval.

## 4. Generate SQL before applying

```bash
dotnet ef migrations script --idempotent \
  --project backend/Watchlist.Api \
  --startup-project backend/Watchlist.Api
```

The idempotent script uses `__EFMigrationsHistory` to decide which migrations still need to run.

CI performs this generation as a metadata/tooling gate.

## 5. Apply locally

```bash
docker compose up -d db

dotnet ef database update \
  --project backend/Watchlist.Api \
  --startup-project backend/Watchlist.Api
```

Then run the API.

## 6. Roll back in a disposable environment

List migrations:

```bash
dotnet ef migrations list \
  --project backend/Watchlist.Api \
  --startup-project backend/Watchlist.Api
```

Move a local database to an earlier migration:

```bash
dotnet ef database update <PreviousMigration> \
  --project backend/Watchlist.Api \
  --startup-project backend/Watchlist.Api
```

For a database that has never had a migration, the target is `0`.

## 7. Shared/production rule

Do not casually remove or rewrite a migration that has already been applied to a shared environment. Prefer a new corrective migration.

For production-style delivery, prefer an explicit deployment job/script with reviewed migration SQL over silently calling `Database.Migrate()` from every application replica at startup.

Why:

- multiple replicas can race for schema ownership;
- schema changes may require longer locks than app startup budgets allow;
- rollout order may require expand/contract compatibility;
- migration privileges can be more restricted than runtime application privileges.

## Expand/contract mental model

For a breaking schema evolution:

```text
expand schema
  -> deploy code compatible with old + new
  -> backfill if needed
  -> switch reads/writes
  -> verify
  -> contract old schema later
```
